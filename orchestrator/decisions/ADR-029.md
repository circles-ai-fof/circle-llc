# ADR-029 — No dynamic tool-use Governor at workflow level

**Status:** Accepted · **Date:** 2026-06-02 · **Supersedes:** none

## Context

Modern multi-agent frameworks (CrewAI, AutoGen, LangChain Agents, OpenAI's
Assistants API) ship with a default pattern: a "Governor" LLM that, at
runtime, decides which tool / agent to call next, in what order, with what
input. The pattern is seductive — it looks like the agent is "reasoning"
about which tool fits the task.

The Circle LLC workflow (EvidenceGateWorkflow) explicitly does NOT use
this pattern. The workflow is a hard-coded linear sequence:

```
idea_hunter → idea_enricher → idea_maturer → market_validator
   → landing_generator → gate_decider
```

This ADR codifies WHY, so a future contributor doesn't get tempted to
"flexibilize" the workflow with a Governor and undo years of debuggability.

## The 3 concrete failure modes a Governor introduces

### 1. Unbounded cost per request

A Governor decides "next step" each turn. If `idea_hunter` calls a tool
that returns "I need more context", the Governor might call `idea_enricher`,
then `web_search`, then `idea_maturer`, then loop back to `idea_hunter`.

What was supposed to be a $0.06 run becomes $0.32 because the LLM made 9
calls instead of 6. Multiply by 100 runs/day and you've burnt $26/day on
nothing.

**Linear workflow guarantees ≤6 LLM calls per run.** Period.

### 2. Zero debuggability when something goes wrong

When `gate_decider` returns KILL for what should have been PASS, with a
linear workflow we can answer "why?" in 10 minutes by inspecting the 6
outputs in order.

With a Governor, the same question requires:
- Inspecting the Governor's decision logs
- Trying to figure out which branch it took
- Realizing the LLM took a different branch this time because of
  temperature noise
- Failing to reproduce the failure

**Linear = reproducible. Governor = unreproducible.**

### 3. Loop deadlock

Agent A calls Agent B which calls Agent A. The Governor sees both calls as
legitimate (each is a different prompt), runs both, and the loop continues
until the request times out. This is **not theoretical** — every major
agent framework has had a loop bug in production within 6 months of
release (cited: CrewAI #1289, AutoGen #2103, LangChain #18444).

**Linear workflows cannot loop. Each step runs exactly once.**

## Decision

The workflow body (Steps 1 → 4b) stays linear, hard-coded,
LLM-non-negotiable. Tool use exists at two specific layers ONLY:

### Layer 1: Per-agent tool use (allowed)

A single agent can use a tool internally:
- `idea_enricher` calls `web_search` (Anthropic native tool) — bounded by
  the agent's max_tokens budget
- `gate_decider` calls the multi-LLM ensemble (M9.0) — bounded to 4 calls

These are NOT Governor patterns because:
- The agent decides ONCE what tool to use, based on its prompt
- The tool returns, the agent's response is final
- No subsequent agent re-runs the prior agent

### Layer 2: Workflow-fixed callbacks (allowed via ADR-028)

A specific agent can invoke a specific other agent in a specific condition,
hard-coded in source. ADR-028 establishes this pattern for the adversarial
callback in `gate_decider`. New callbacks require their own ADR.

### Forbidden: dynamic dispatch

These are explicitly OUT:
- LLM-controlled "next agent" routing
- Loop-back / recursive agent calls
- Free conversation between agents
- "Manager" agent that reads outputs and decides what to do next

## When to revisit

Two conditions would justify a future ADR overturning this:

1. **N≥10 production fábricas** AND evidence that linear workflow misses
   real opportunities (concrete: at least 3 documented cases where a
   linear KILL was a real PASS, fixable only by re-routing mid-workflow).

2. **A new framework with provable cost+loop bounds** ships in production.
   Current state-of-the-art (2026 Q2) still has the failure modes above.
   If that changes, revisit.

Until then: **linear is the answer**. We trade flexibility for
debuggability, cost-predictability, and operational simplicity. It's
the right trade for a system that handles money decisions.
