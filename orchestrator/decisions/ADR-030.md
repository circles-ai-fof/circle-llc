# ADR-030 — SQLite → Postgres + pgvector migration plan

**Status:** Accepted (plan) · **Date:** 2026-06-03 · **Supersedes:** none ·
**Activation trigger:** N ≥ 3 fábricas activas O sostained write contention
> 5 % de los requests.

## Context

El stack actual usa SQLite con WAL en un volumen persistente de Railway.
Esa elección es deliberada (Reganti Cap 10 §10.3 — "stay at the simplest
level that handles 90 % of your cases") y sigue siendo la correcta para el
estado actual (1 fábrica activa, N=1).

Esta ADR no migra hoy. Codifica **qué tiene que pasar antes** de migrar y
**cómo se hará** cuando llegue el momento, para que la decisión sea
mecánica y no requiera otra ronda de diseño.

## Pre-condiciones para activar la migración

Los 5 deben cumplirse — cualquiera por sí solo NO justifica migrar.

1. **N ≥ 3 fábricas activas** con `outcome_insights` writable=True
   (R10). Es la condición principal: outcome_db sin escritura cruzada
   es un dataset estático y SQLite lo aguanta.
2. **pgvector necesario.** Al menos un agente (probablemente
   `outcome_retriever` post-M17) requiere semantic search sobre
   embeddings con > 10 000 vectores. SQLite no tiene índice ANN.
3. **Contention real.** Métrica: > 5 % de requests con `SQLITE_BUSY`
   o `database is locked` en los logs de los últimos 7 días.
4. **Backup R2 saludable.** Los backups diarios de M11.2 deben tener
   ≥ 30 días consecutivos verdes. Sin eso, migración es prematura
   (no hay rollback).
5. **Test suite ≥ 1 500 tests verdes.** Cada componente que toca DB
   debe tener su test mock + test real (Postgres en contenedor).
   Esto exige un sprint dedicado (M16+) antes de M17.

## Decisión (cuando se active)

### Stack target

- **Postgres 16** (versión LTS, no beta).
- **pgvector ≥ 0.7.0** para columnas de embeddings.
- **Hosting:** Railway Postgres add-on (consistencia con resto del stack).
- **Conexión:** `psycopg[binary,pool]` + SQLAlchemy 2.x async.
- **Migraciones:** Alembic con autogenerate (NO Django, NO Prisma).

### Esquemas

Cada `*_store.py` en `orchestrator/core/storage.py` se convierte en una
tabla con su misma columna set. Sin renombrar campos — minimiza
riesgo de regresión.

Cambios estructurales solo donde Postgres lo exija:
- `signals.timestamp` → `TIMESTAMPTZ` (era `INTEGER` epoch en SQLite).
- `signals.embedding` → `VECTOR(384)` (era `BLOB` con numpy bytes).
- `*_at` columns → `TIMESTAMPTZ` con `DEFAULT now()`.
- Índice `ivfflat` sobre `signals.embedding` con `lists = sqrt(rows)`.

### Multi-tenant (M5+ deferido, ahora viable)

Postgres + Row Level Security (RLS) habilita multi-tenant. Plan:
1. Añadir columna `tenant_id UUID NOT NULL` a TODAS las tablas
   (default a un UUID estático = la fábrica original durante la
   migración inicial).
2. Activar `ENABLE ROW LEVEL SECURITY` por tabla.
3. Policy `tenant_isolation`: `USING (tenant_id = current_setting('app.tenant_id')::uuid)`.
4. Connection pool setea `SET app.tenant_id = $tenant` per-request.

NO hacer multi-tenant en M17 si solo migra una fábrica — añadir RLS
sin tenants reales es complejidad muerta. Es una sub-decisión que
revisitamos cuando llega el segundo cliente.

## Migration steps (cuando se ejecute)

### Pre-flight (1 día)

1. Dump SQLite → `.sql` con `sqlite3 .dump`.
2. Convertir a Postgres con `pgloader` (script en `scripts/pg_migrate.py`).
3. Validar conteos: `SELECT COUNT(*) FROM <tabla>` debe matchear ±0
   entre SQLite y Postgres.

### Cutover (window de 2 horas con feature flag)

1. **T-2h:** Activar modo `DUAL_WRITE=true` — todo write va a SQLite Y
   Postgres. Reads siguen en SQLite.
2. **T-1h:** Validar parity: query random sample de 100 signals,
   100 ideas, 100 runs en ambas DBs. Debe ser idéntico.
3. **T-0:** Cambiar `DB_BACKEND=postgres`. Reads ahora desde Postgres.
4. **T+15min:** Si OK, desactivar `DUAL_WRITE`. Si falla, revertir
   `DB_BACKEND=sqlite` (datos siguen ahí).
5. **T+24h:** Si verde, declarar SQLite legacy. Mantener como backup
   30 días más antes de archivar.

### Rollback

Si en T+0 a T+15min algo rompe:
1. `DB_BACKEND=sqlite` (env var en Railway).
2. Postgres queda como sombra hasta investigar.
3. Datos escritos a Postgres durante DUAL_WRITE se pierden — son
   los mismos que en SQLite porque dual-write era idempotente.

## Lo que NO se migra

- `app.db` de tests (siempre SQLite in-memory).
- Snapshots SQLite en `data/snapshots/` (legacy, archivar tras 30d).
- `outcome.db` mientras `R10 outcome_insights writable=False` esté
  activo. La outcome_db se inicializa directamente en Postgres
  cuando se active escritura (R10 → outcome_db_writable=True).

## Costo y timing

- **Railway Postgres add-on:** ~$5/mes hasta 1 GB, ~$15/mes a partir.
- **Dev cost:** 3 sprints (M17.0, M17.1, M17.2) — ~6 días-persona.
- **Test cost:** 500 tests nuevos para parity SQLite↔Postgres (M16
  los empieza a sembrar).
- **Operacional:** Backup `pg_dump` diario a R2 reemplaza el backup
  SQLite de M11.2 (mismo cron, distinto comando).

## Anti-patterns prohibidos durante la migración

- **NO** usar Postgres como write-through cache de SQLite. O
  Postgres es source-of-truth o no lo es.
- **NO** introducir un ORM nuevo en el mismo sprint (SQLAlchemy ya
  es suficiente). Cambiar a Tortoise/Beanie + migrar DB es dos
  riesgos a la vez.
- **NO** migrar y multi-tenant al mismo tiempo. Primero migración
  con tenant único, luego RLS en sprint separado.
- **NO** activar pgvector si no hay un agente que efectivamente
  consulte por similarity > top-50. La conversión BLOB→VECTOR
  cuesta tiempo de cutover.

## Indicadores de éxito

A los 30 días post-migración:
- p95 read latency ≤ SQLite baseline (target: ≤ 80 ms).
- p95 write latency ≤ 2× SQLite (esperado por commit fsync).
- 0 `database is locked` errors.
- Backup `pg_dump` en R2 con < 1 hora de retraso vs cron schedule.
- Tests verdes en CI sin cambios de mock (la abstracción del store
  debe ocultar el backend).

Si cualquiera falla, el rollback está documentado arriba.
